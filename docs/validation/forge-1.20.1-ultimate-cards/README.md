# Ultimate Capacity / Ultimate Overclock acceptance

Scope: the two Ultimate upgrade cards, `jdte:ultimate_capacity_upgrade` and
`jdte:ultimate_overclock_upgrade`, on the machine families the 1.21.1 source never
intercepts (the default branch of `UpgradeHelper.isUpgradeCompatible`).

Status before this round: **P**, because the Forge branch carried a port-side
whitelist that only admitted the cards into 27 families, so the source behaviour
was missing on every other host.

Status after this round: **V**, scoped as described under "Boundaries".

## What changed in the code

`UpgradeHelper.isUpgradeCompatible` now reproduces the source shape instead of
layering a whitelist on top of it: the intercepting families keep their source
lists and every other type and family falls through to the source default branch.
See the "Upgrade-gate parity checkpoint" in the [port log](../forge-1.20.1-port.md).

Nothing family-specific was added. The behaviour comes from hooks that already
existed: `adjustEnergyCapacity` (x50), `adjustEnergyCost` (x50),
`getEffectiveTickSpeed` (locked delay to 1 tick) and the ten ticker executions in
`BaseMachineBlockMixin`.

## GameTest evidence

`UltimateDefaultBranchGameTests` (4 tests) drives the physical machines rather
than the helper arithmetic:

| Test | What it proves |
| --- | --- |
| `glueActivatorPhysicalCapacityCostAndTicker` | Advanced glue activator: baseline 50,000 FE capacity and 500 FE cost; Ultimate Capacity gives a real x50 buffer (2,500,000) that really stores that much; Ultimate Overclock charges the real x50 cost (25,000); removing the capacity card truncates stored FE to the shrunk buffer. |
| `lootFabricatorPhysicalCapacityFluidAndLockedSpeed` | Loot fabricator: baseline 500,000 FE / 64,000 mB / 5,000 FE cost; Ultimate Capacity gives a real x50 FE buffer and x50 fluid tank; Ultimate Overclock charges x50 and locks the process time to one tick. |
| `lootFabricatorUltimateCardsExclusiveAndSurviveReload` | Speed cards stay mutually exclusive, each Ultimate card is capped at one, both survive save/reload through the fabricator's dedicated handler, and the reloaded machine reaches its x50 buffer on the first real ticker tick. |
| `glueActivatorSpeedCardsExclusive` | The glue activator rejects the other speed cards and a second Ultimate Overclock while still accepting Ultimate Capacity and an ordinary Filter card alongside them. |

`Ultimate27GameTests` keeps covering the intercepted families: the gate, the
install path, the helper arithmetic, save/reload and the ten-execution ticker for
41 tiers over 27 roots, with the advanced item collector as the negative control
(it takes neither card) and the suppressor/blocker pair taking Ultimate Capacity
only.

Executed in the `Forge 1.20.1 GameTests` workflow: **All 421 required tests
passed** (417 before this round plus the 4 above), run
[44511706746](https://github.com/rulanup/JDTE/actions/runs/44511706746).

## Boundaries

This is scoped acceptance, not a proof for every host:

- GameTest coverage of the physical effects is on the advanced glue activator and
  the loot fabricator, plus the helper/gate coverage across the 27 intercepted
  roots. Native JDT machines, the time freezer, the extended generators, the
  extended experience holder and the extended energy transmitter reach the same
  default branch but do not each have their own physical-effect test.
- The real-client run covers the glue activator and loot fabricator GUIs, the
  creative tab, JEI and baked models. It does not re-validate every host screen.
- No packaged dedicated-server unload/restart round was run for these two cards.
  The earlier item-sender and fluid-sender acceptance did run that round for
  their own hosts.
- Prolonged multiplayer and arbitrary mod combinations remain unverified.

## Reproducing

```bash
# GameTest half (server side, physical effects)
bash gradlew runGameTestServer

# Real-client half (needs a world; the workflow stages one from the GameTest server)
bash gradlew runClient -PjdteUltimateSmoke
```

On a developer machine `scripts/run_fluid_sender_client_smoke.sh` shows the same
world-staging pattern for the client smoke runs.
